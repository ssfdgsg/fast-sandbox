# Fast dual-GPU qualification

Use a dedicated native Linux x86_64 host with two idle, exclusively reserved NVIDIA GPU UUIDs, root, writable cgroup v2, and mount/network administration. The lightweight path uses Python standard-library ctypes and native CDI driver libraries; it executes a PTX int32 32x32 matrix multiply and compares all 1,024 outputs with a CPU reference on every assigned GPU. It requires neither PyTorch nor a CUDA toolkit in the Sandbox image. NVIDIA host driver and Container Toolkit/CDI remain required.

The hardware tests clear CUDA_VISIBLE_DEVICES before driver initialization so an image cannot hide an accidentally exposed card. Physical GPU identity is obtained by mapping CUDA PCI bus IDs to NVML UUIDs; CUDA and NVML indexes must never be assumed identical. These probes target native Linux whole GPUs; they do not certify WSL per-device isolation, MIG or privileged-host isolation.

## Prepared paths

- `run-dual.sh`: real dual-container CUDA, concurrent admission, exact UUID sets, exhaustion, idempotency, deletion/reuse, manager recovery, CPU isolation, a two-GPU Sandbox, and two independent driver instances sharing the node journal.
- `run-driver.sh`: original one-GPU PyTorch test, retained for framework verification.
- `cluster-smoke.py`: Kubernetes-native Pool allocation and CUDA assertions; see its help and the full `PLAN.md` for remaining fault gates.
- `bin/`: precompiled Linux/amd64 component binaries in the prepared delivery.

One invocation of `run-dual.sh` runs each new hardware test once; set `FSB_GPU_E2E_ROUNDS=10` for ten serial rounds. It is not a performance benchmark. A successful test is separate from Kubernetes/Fastlet process crash acceptance.

## Execution order

1. Inspect host privileges, GPUs, installed runtimes and existing allocations. Stop immediately if an ordinary development container lacks host-level capabilities; do not spend rental time attempting unsupported nested setup.
2. Prefer an existing functional driver/containerd/toolkit. Import the prebuilt Python image into the selected daemon's `k8s.io` namespace. Generate or refresh UUID-named CDI definitions without conflicting spec files.
3. Run the dual-GPU driver tests first. The script rejects skipped hardware tests and saves output and cleanup diagnostics.
4. Use a preexisting cluster, or the prepared native test cluster, import prebuilt FastSandbox images, deploy the current CRDs/components, and run Kubernetes tests. Stop competing allocators before direct tests; never reserve the same devices in both phases at once.
5. Run the original PyTorch test with the supplied Huawei mirror if available. Its CUDA result and runtime cleanup must both pass.
6. Exercise actual Fastlet restart/Pod replacement and capacity changes, collect evidence, then clean exact test ownership. Record any unrun `PLAN.md` gates explicitly.

```bash
sudo ctr --address /run/containerd/containerd.sock -n k8s.io images import python-amd64.tar
sudo env FSB_GPU_E2E_DEVICES=GPU-UUID1,GPU-UUID2 \
  FSB_GPU_E2E_IMAGE=docker.io/library/python:3.11-slim-bookworm \
  bash run-dual.sh /tmp/fsb-gpu-results/dual-01
```

For K3s, supply its actual socket in `FSB_GPU_E2E_SOCKET` and import into that daemon, not another host containerd. Use explicitly reserved UUIDs from the host inventory; do not blindly take the first two cards on a shared server.

The user-supplied optional PyTorch mirror is `swr.cn-north-4.myhuaweicloud.com/ddn-k8s/docker.io/pytorch/pytorch:2.4.0-cuda12.4-cudnn9-devel`. Its manifest was reachable with digest `sha256:e96c6896ecfbb50d89c87bf94110206ef444f27268c5f72201eb29fba9c90331`. This is an artifact identity check, not proof of real CUDA execution. Prefer reuse if already present; the lightweight test avoids requiring this large development image before first hardware feedback.

## First SSH action and offline packages

Run `sudo bash fast-host-check.sh` before any installation or image pull. A root shell in a restricted GPU container does not meet the host requirements. If the rental platform asks for a PyTorch boot image, that choice alone does not establish host privileges. Stop immediately on missing capabilities or read-only cgroups and resolve the rental type before spending time on nested containerd.

The prepared delivery splits the small Python image/driver kit from the larger cluster images so they can transfer and run first while cluster assets transfer in parallel. `core-images.tar.gz`, `python-amd64.tar.gz`, and `device-plugin.tar.gz` contain Linux/amd64 images only. Import with `gzip -dc ARCHIVE | ctr --address SOCKET -n k8s.io images import -`. The optional `cluster-assets/` contains official checksum-verified K3s 1.35.0 binaries/airgap images; `toolkit-debs/` contains four official checksum-verified NVIDIA Container Toolkit 1.18.0 packages. Keep a functional installed driver/toolkit; do not replace it automatically.

On an otherwise empty dedicated host, install the toolkit packages only if missing (verify `SHA256SUMS`, then use `dpkg -i` and resolve any OS dependencies). `install-test-cluster.sh cluster-assets --dedicated-empty-host` starts the optional local test cluster, without replacing an existing cluster or host GPU driver. It requires systemd; adapt explicitly for other init systems. Toolkit installation precedes K3s startup so the NVIDIA runtime can be detected. Use the cluster's actual socket/root and kubelet root when calling `deploy-test-stack.py`. The disposable Janitor uses 10-second scan and orphan grace intervals; this is a test setting, not a production recommendation.

After importing all images, generate driver fixtures with `render.py --probe driver --slots 2 --image docker.io/library/python:3.11-slim-bookworm --namespace fsb-gpu-dual --output FIXTURES`. Run `cluster-smoke.py --fixtures FIXTURES --output RESULTS --include-faults --include-capacity` for the selected real cluster gates. Failure retains the isolated namespace for diagnostics; success removes exact test ownership. This does not replace all 29 gates in `PLAN.md`.
